# Objective

UI0B connects the owned UI0A application contract to Phoenix's existing,
read-only file inspection and 166-byte project parser. It deliberately stops
before compatibility-profile matching and export.

# Scope

`AppService` accepts one path-based `InspectProjectRequest`, reads and hashes
the file, creates an opaque session, and returns owned project and sequence
summaries. It retains the source identity and bytes for a later revalidation
step; no parser borrow escapes the call.

# AppService

`src/app_service.rs` owns a synchronous service with an in-memory session map.
Session IDs are deterministic opaque values (`session-00000001`, etc.) and are
generated by the service, never from paths, names, hashes, or offsets.

# Session lifecycle

UI0B uses lifetime ownership: sessions remain available until the `AppService`
instance is dropped. There is no expiry, timer, global state, or explicit close
operation yet. Multiple sessions are supported.

# Internal session state

The private session record stores the requested path, source bytes, byte size
and SHA-256, the owned inspection response, and bounded diagnostics. A future
export operation must re-read and re-hash before relying on this identity.

# File reads

Standard Rust file APIs are used. Open, metadata, canonicalization, and read
failures map to `FileUnreadable` / `InspectProject` with diagnostic code
`file_read_failed`. Readable arbitrary files remain inspectable assessments.

# Contract-version handling

Requests must carry `CONTRACT_VERSION` (currently 1). A mismatch returns
`InternalError` with `contract_version_mismatch`; no parser work is attempted.

# Identification

The existing Finder metadata identification helper is reused where available.
Structural parsing is the stronger application-facing recognition signal. The
service does not expose Finder bytes or raw evidence in the normal summary.

# Parser-profile selection

The established `parse_project_166` parser is attempted only as the current
known structural profile. A successful parse is labeled `Descriptor166`.
There is no claim that every recognized Studio Vision file uses this profile.

# Unrecognized files

Readable input that does not parse as the established profile returns a
successful response with zero sequences and `Unknown` readiness (or
`Unsupported` when Finder metadata positively recognized Studio Vision but the
profile rejected the structure). This keeps inspection distinct from an
unreadable-file operation error.

# Parser failure mapping

Parser failures are retained in bounded diagnostics and a project warning;
Rust parser debug output is not used as the primary display message.

# Sequence enumeration

Successfully parsed sequences are emitted in parser structural order. Each is
assigned a session-scoped ID of the form `<session>-sequence-0001`. Names are
used only for display; duplicate names remain distinct.

# Sequence identity

The DTO exposes only the opaque `SequenceId`. Structural ranges and parser
records remain private to Core and are not public identity.

# Names

Valid UTF-8 sequence names are copied. Invalid legacy bytes use the bounded
placeholder `Unnamed Sequence`; no new MacRoman dependency or reinterpretation
was introduced.

# Readiness mapping

Parsed sequences with ordinal descriptor/pair association are
`PartiallySupported` with `MissingChannelRouting`. Unresolved associations are
`PartiallySupported` with `IncompleteSequenceStructure`. No generic sequence is
`Ready`, because UI0B has no general routing or compatibility profile.

# Project overall readiness

Readiness is computed in Core: Ready has highest precedence, then
PartiallySupported, Unsupported, and Unknown. A parsed sequence therefore makes
the project partially supported; an empty/unrecognized assessment remains
conservative.

# Warnings

Warnings are owned, scoped, source-ordered DTOs and use the UI0A deterministic
ordering helper. Routing uncertainty is a data-loss-risk warning; it is never
paired with Ready.

# Diagnostics

`None` returns bounded structural fields without hash/evidence/error detail;
`Summary` adds identification and structural status; `Full` additionally
returns SHA-256 and technical parser context. Raw bytes and hex dumps are never
returned. Diagnostics retrieval fails deterministically with `unknown_session`
for an invalid ID.

# Source revalidation seam

`source_identity` exposes only path, byte size, and SHA-256 to future Core code.
UI0B does not export, but UI0D must verify these values before using a session.

# Ownership

All returned DTO strings, vectors, IDs, and diagnostics are owned. Source bytes
are retained privately by the session. No borrowed parser lifetime crosses the
service boundary.

# Tests

`tests/app_service.rs` covers service/session identity, missing files, contract
versions, readable unrecognized files, diagnostics levels, source identity,
unknown sessions, and optional authentic-fixture sequence order.

# Authentic fixture policy

The fixture test is optional and returns cleanly when the established external
artifact is absent. It never copies or modifies research artifacts and does not
apply Ode export policy.

# Explicit exclusions

UI0B adds no FFI, serialization, UI, export writing, compatibility-profile
registry, channel derivation, event walking, or CLI behavior. It contains no
authenticated Ode constants.

# UI0C2 status

The accumulated ProfileEvidence adapter extends this inspection snapshot with
validated Descriptor166 event bounds, bounded-walker family/count inventory,
and only the separately audited generic Patch observations. UI0B readiness and
export capability remain unchanged; compatibility-registry assessment is still
deferred.

# UI0C4 handoff design

Assessment is a later Core pass over retained evidence: each opaque
`SequenceId` is mapped to its structural ordinal independently, and matched
policies remain private to that session. Inspection remains useful for NoMatch
and Rejected sequences; export must revalidate source identity before use.

# UI0C4A implementation status

AppService now performs this internal assessment after inspection using the
built-in or injected registry. The public inspection response remains the
unchanged UI0B response until a later readiness-projection phase.

# UI0B gate

The implementation provides path inspection, owned sessions and DTOs,
conservative readiness, bounded diagnostics, and the future source identity
seam while preserving existing parser semantics.

# Single recommended next step

Design UI0C's Core-only compatibility-profile registry seam without embedding
Ode constants in the generic service or contract modules.

# UI0C handoff

UI0C should add registry assessment after generic parsing while preserving the
current conservative UI0B result for no-match and rejected profiles. Only a
complete exact match may change a sequence to Ready; the frontend must remain
unaware of profile internals.

# UI0C2 evidence adapter

Parsed sessions retain a private structural snapshot and expose Core-only
`ProfileEvidence`. Raw name/range and descriptor/pair facts are copied exactly;
channels, Patch facts, decoded families, and exact event ranges remain absent
where generic parser evidence is not established. This does not call the
registry or change UI0B readiness.

## UI0C2B exact bounds

For Descriptor166 sessions, the structural snapshot records an exact event range
only after the parser validates the terminal seven-byte grammar. A bounds
failure leaves that field unavailable. Readiness, export capability, decoded
families, Patch evidence, and observed channels are unchanged.

## UI0C2D Patch evidence

The shared walk also supplies bounded Patch observations. AppService preserves
their source ranges and direct program bytes with deterministic ordinals, while
leaving bank fields, routing, readiness, and export capability conservative.

## UI0C2C family inventory

AppService reuses the bounded mixed-event walker over validated Descriptor166
ranges. It records canonical family presence and logical counts while retaining
`patch_evidence` empty, `observed_channel` unset, conservative readiness, and no
export capability.

## UI0C4B source revalidation

The stored inspection path can be explicitly revalidated without changing the
inspection DTOs. Core rereads and hashes the file, reparses it, rebuilds owned
evidence, and reruns the registry for the original structural sequence ordinal.
Only an equivalent fresh policy and fresh owned bytes are eligible for a later
export handoff; stale session policy is never treated as authorization.
