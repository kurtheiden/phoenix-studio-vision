# Bounded equivalent duplicate Note source order

The SourceOrder serializer previously refused a second positive Note attack at
one tick for the same channel and pitch, even after unique retained source
ordinals had established its order. The focused SCHOOL review found one shared
case across four completely decoded Tracks:

| Sequence / source Track unit | Logical events | Duplicate collision points |
| --- | ---: | ---: |
| DANCING.MID / 5 (C4-Brass) | 272 | 1 |
| NOTHING.MID / 9 (C10-Drums & Per) | 1,120 | 2 |
| M-vegetarian del / 2 (bass & snare) | 303 | 8 |
| M-vegetarian #2 / 19 (bass & snare) | 537 | 17 |
| Total | 2,232 | 28 |

These source units include the two conductor units; they are not an instruction
to reorder visible ordinary Tracks. The review retained distinct adjacent Note
representations and increasing source ordinals for every collision. Each pair
had identical channel, pitch, start, attack velocity, release velocity, duration
and generated release tick. There was no ambiguity about physical source order.

## Production boundary and bounded contract

DecodedExportEvent retains its source range. The adapter now carries that range
in ExportTrackResult.note_provenance, keyed by the existing even attack ordinal.
ScheduledEvent and its ordering contract are unchanged. Bounded sequence assembly
passes this provenance to serialize_named_musical_track_with_note_provenance.
The older serializer APIs still refuse this duplicate case without provenance.
Neither API grants export authorization.

The new API accepts exactly two coincident positive attacks only when:

- their complete NoteOn messages match and their start ticks match;
- their unique, distinct, increasing attack ordinals are even;
- each has exactly one nonempty source range, and the first range ends exactly
  where the second begins (adjacent, nonoverlapping, source order corroborated);
- each has exactly one generated release at its own attack ordinal plus one;
- the release messages match, target the attacks' channel/pitch, and share a tick
  strictly after the start.

Equal start and end ticks establish equal positive duration exactly; complete
message equality establishes channel, pitch and both velocities. Unique even/odd
ordinals establish release parentage. Both attacks and both releases are emitted,
in existing tick/source-ordinal order. Nothing is merged, deduplicated or retimed.
Zero-duration handling continues through the existing own-start/own-end rule.

Missing, duplicate, reversed, empty, overlapping or nonadjacent source ranges,
ambiguous ordinals, missing/mismatched endings, unequal velocities or durations,
and a third coincident attack remain refused. Different channels/keys follow
existing independent semantics. Patch expansion checks, unsafe ending checks,
priority-mode behavior and all decoding/routing/conductor/readiness policies are
unchanged. This is **not a general same-pitch retrigger or overlapping-voice rule**.

## Verification

Focused synthetic tests cover duplicate multiplicity, deterministic ordering,
independent collisions with surrounding Controller events, channel independence,
provenance and release-parentage refusals, and unchanged existing ordering cases.
The bounded-sequence regression formerly asserting refusal of identical adjacent
Notes now checks unequal attacks; a new positive test preserves both Notes.

The production-based bounded SCHOOL assessment accepts all four Tracks and all
28 collision points. Independent in-memory MTrk readback matches every scheduled
Note attack and release in order, including pitch, velocity, channel and tick:
2,229 Note attacks, 2,229 releases and three source-channel Controllers across the
four Tracks. All 2,232 logical events remain represented. The 28 collision points
represent 56 source Notes, not additional logical events.

The whole-project assessment changes only these four Track gates: SourceOrder
refusals fall from four to zero, with no previously passing Track regression and
no change to event counts. Nothing FINAL remains 15/15. Sequence classifications
remain unchanged. DANCING.MID remains PARTIAL because of its separate sequence
terminal-envelope certification refusal; this task does not investigate it.
No recovery MIDI file is generated by this verification.
